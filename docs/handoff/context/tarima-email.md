## 3. Recommendation

### Dev/test stack (pick)

Keep the two-layer dev seam and upgrade the mock layer to MailDev 3. Layer 1 stays the SQLite loopback (EMAIL_LOOPBACK_DOMAINS=tarima.test, loopback_inbox, GET /internal/admin/inbox): deterministic, zero deps, already asserted by packages/channels/test/email.test.ts and the e2e smoke. Layer 2 replaces the hand-rolled 67-line mail-mock.mjs with MailDev 3 embedded in the existing mock-boot child process: it is TypeScript on the Nodemailer engine, MIT, lets vitest/harnesses bind ephemeral ports programmatically (SMTPServer#getPort / APIServer#getPort shipped in 3.0.0), gives humans a real web UI to inspect HTML renders on :3513, and gives agents an MCP server so a coding agent can answer "did the email go out" mid-task.

Rejected dev alternative: the transcript's embedded smtp-server + mailparser hub. Reason: it is the engine MailDev already wraps, so embedding raw would mean owning protocol, storage, and permissions code that a single-user dev environment does not need; the fine-grained per-agent RBAC in that sample solves a problem tarima does not have (dev identities are not permission boundaries, the loopback to= filter plus agent-scoped tools already isolate work). Inbucket and Mailpit remain valid fallbacks but both are non-node binaries with an install step per dev machine and per CI job, against the repo's node-only mock convention.

### Production stack (pick)

Keep Brevo for transactional (N1/N2): verified sender, whitelisted VPS IP, working free tier, zero code change. For agent outbound (N6), keep Brevo but give the agent its own sending identity on a dedicated subdomain (e.g. outreach.tarima.events, DNS on the existing Cloudflare zone): verify the subdomain in Brevo, publish SPF (include Brevo), DKIM, DMARC (p=none with rua, tightening later), and add a second MAIL_FROM env (e.g. MAIL_FROM_OUTREACH) consumed by the drain. This is GTM gap G8 made concrete and quarantines any reputation damage away from OTP mail. At the planned warm-list volume (15-20 approved sends/week) Brevo's free 300/day is ample.

Rejected production alternative: the transcript's Google Workspace mailbox-per-agent via SMTP/IMAP. Reason: right answer for true cold outreach at volume (mailbox-provider reputation), wrong cost/benefit here: it adds a paid seat, OAuth or app-password plumbing, IMAP polling (imapflow) where an HTTP seam already exists, and it re-introduces per-agent mailboxes tarima does not need under HITL. Resend and Postmark were also considered for transactional DX; both are sound but add a second provider to operate while the current one works, and Resend's AUP caps complaint/bounce rates that unattended agent sends could trip. Cloudflare Email Sending stays on watch until it exits Beta.

### Identity model

Users keep no mail identity (their channels are in-app/telegram/whatsapp; OTP goes to their login address). Agents get environment-class identities, not per-agent ones: notifications@tarima.illo.fyi for transactional (unchanged) and outreach@outreach.tarima.events for agent RFQs. Per-agent addresses multiply reputation surfaces andbuy nothing at 15-20 sends/week with a human clicking every send; if personas come later, add local parts on the same subdomain (outreach-alice@) so DKIM alignment holds. Projects map to entities: every drained agent email carries Reply-To rfq+<entityId>@outreach.tarima.events. Plus-addressing was chosen over VERP because the catch-all-to-worker path already exists and decodes the full to address (webhooks.ts:112), and VERP's bounce-routing benefit is moot at volumes where Brevo's dashboard shows bounces; the fallback if some receiver strips plus tags is the plain local part rfq-<entityId>@, same decode, same catch-all.

### Inbound path

Unchanged transport, new consumer: venue replies to rfq+<entityId>@outreach.tarima.events; Cloudflare Email Routing catch-all on the outreach subdomain fires apps/inbound-worker; the worker posts {raw,to,from} to POST /webhooks/email with X-Webhook-Secret (webhooks.ts:99-119); postal-mime parses (mime.ts:44-63); T6 decodes the entity, writes outreach_messages, and emits an event so the agent's next turn sees the answer. Threading across turns: store Message-ID at drain time and References on reply; the mime parser already surfaces messageId and threadId. Dev mirror of this path: no Cloudflare needed; tests post synthetic MIME straight to /webhooks/email (pattern already in apps/api/src/routes/webhooks.test.ts).

### Risks

Deliverability: agent-sent RFQs from a shared transactional IP can land in Promotions/Spam; mitigate with the separate outreach subdomain, plain-text-first bodies, no tracking pixels, per-day caps (30-40/inbox/day during warm-up, per the transcript's cadence rules), and HITL human review of every first contact. SPF/DKIM/DMARC: Brevo provides DKIM and SPF includes per verified domain; publish DMARC p=none with reporting first, move to quarantine only after monitoring; misconfigured records risk OTP mail, which is why the subdomain is quarantined from the start. Warm-up: the outreach subdomain starts cold regardless of the primary domain's age; start with the founder's real warm list only. Abuse: an agent can hallucinate recipients or resend spam; mitigations already exist (approval: always() plus agent-wide outbound policy, approval.ts:31-37; idempotency keys, send_email.ts:45-54) and T4 adds rate limiting per recipient domain. GDPR/LSSI: cold email into Spain is not compliant without consent (GTM line 114); the agent's outbound scope must stay warm-list, and the suppression list (T4) must honor opt-outs within 10 business days. Privacy: loopback_inbox stores OTP codes and /internal/admin/inbox must remain prod-gated (it is, auth.ts:167-169); MailDev's MCP and web UI are unauthenticated, local-only by binding, never expose publicly.
